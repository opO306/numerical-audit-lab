## B3 — Physical r_min / domain binding

원본 후보:

```text
r_min =
1200000000000 / 529177210903 bohr
```

를 Lab에서 사용할 physical binding으로 명시적으로 승인할지 결정하고 provenance와 함께 고정하십시오.

중요:

`r_min`은 단순 drift guard만의 값이 아닙니다.

설계 감사 판정은:

```text
C:
Impulse admission에도 필요
Drift segment guard에도 필요
```

입니다.

따라서 physical Impulse oracle은:

```text
R < r_min
```

상태를 force 계산 전에 physical-domain refusal로 처리하는 계약이 필요합니다.

다음도 명시하십시오.

```text
R = 0
R < r_min
R = r_min
R > r_min
```

각 경우의 의미와 우선순위.

기존 Arithmetic V1의 generic supplied-threshold geometry PASS를 physical r_min binding 완료로 간주하지 마십시오.

## B4 — Proof wire / resource contract

Impulse certificate/proof artifact의 wire contract를 새로 고정하십시오.

Arithmetic V1의 F-CLAIM-1에서 이미 결과 serialization 경계가 실제 FAIL을 만들었으므로 이번에는 사전에 닫습니다.

최소한 다음 한도를 정의하십시오.

```text

canonical reduction
integer digit limit
total artifact byte limit
list/array length
nesting depth
metadata length
attempt/history count
diagnostic size
certificate size
```

Canonical rational은 반드시:

```text
exact reduction
→ output size check
→ decimal/string serialization
```

순서로 처리하는 계약이어야 합니다.

process-global integer-string limit을 변경하는 방식은 사용하지 않습니다.

Proof가 너무 커서 publication할 수 없을 경우:

```text
계산 성공
≠
proof publication 성공
```

을 분리하십시오.

Partial raw J만 먼저 공개해서 성공으로 처리하지 마십시오.

Resource failure도 bounded structured record여야 하며, 거대한 integer나 payload 전체를 failure message에 다시 넣지 마십시오.

## B5 — Finite computation policy

Precision escalation의 **유한 policy**를 작성하십시오.

단, 감사자가 명시적으로 budget 숫자를 임의 선정하지 않았으므로 이번에도 근거 없이 숫자를 박지 마십시오.

먼저 다음을 정의하십시오.

```text
N의 의미
P의 의미

exp Taylor/order parameter
radius refinement parameter
attempt sequence

integer bit cap
rational numerator/denominator bit cap
temporary allocation cap
work-unit accounting
artifact-size interaction

STOP priority
resource failure priority
programming fault 처리
```

그리고:

```text
internal enclosure convergence

rounding cell decision

finite-budget resolution

proof-wire publication
```

을 서로 다른 명제로 분리하십시오.

V1은 모든 admissible input에서 성공할 필요가 없습니다.

다음 계약을 허용할 수 있습니다.

```text
soundness guaranteed
finite budget에서 못 풀면 UNPROVED / STOP
```

그러나 그 정책을 명시해야 합니다.

절대:

```text
budget 소진
→ 마지막 approximation 반올림
```

으로 진행하지 마십시오.

### B4와 B5 공동 검토

Proof wire와 precision budget은 따로 승인하지 마십시오.

예를 들어 dyadic denominator가 실제 `2^P`로 남는 경우:

```text
2^13606 < 10^4096 <= 2^13607
```

이므로 4096자리 wire와 높은 P가 충돌할 수 있습니다.

따라서:

```text
B4 proof representation
+
B5 precision/work budget
```

을 하나의 호환성 검토 대상으로 다루십시오.

## B6 — Independent rechecker lineage

아래 중 어떤 구조를 공식 V1로 채택할지 결정하십시오.

후보 A:

```text
새 Impulse producer
+
새 독립 rechecker
```

후보 B:

```text
새 Lab binding/producer
+
기존 exact checker V1/V2 중 감사 가능한 하나
```

단, “독립 계산기가 많을수록 좋다”는 이유만으로 새 nonlinear 엔진을 하나 더 만들지 마십시오.

각 안에 대해:

```text
공유 TCB
공유 specification
공유 constants
공유 parser
공유 certificate schema

공유 금지 primitive helper
공유 금지 enclosure helper
공유 금지 rounding implementation
공유 금지 executor helper
```

를 표로 정리하십시오.

Point Prover는 Checker V2의:

```text
K2.enclosure(...)
K2.check_certificate(...)
```

를 사용하므로:

```text
Point Prover
+
Checker V2
```

를 서로 독립된 두 oracle로 세지 마십시오.

Rechecker가 producer가 써 준 최종 interval을 받아 rounding cell만 확인하는 구조도 충분하지 않습니다.

Rechecker는 원래 state/spec에서 nonlinear proof를 다시 구성하거나, 각 primitive witness와 합성의 soundness를 독립적으로 확인해야 합니다.

또 위조된 좁은 interval, 다른 constants, 누락 derivative term 등이 포함된 valid-looking certificate를 거부할 수 있어야 합니다.
